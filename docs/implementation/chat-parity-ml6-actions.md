## Opus integration

### Forwarding

1. Use the existing per-chat context path. Put a room-scoped Forward action beside `ChatPinMenu` in the environment. Use `model.roomForwardMenuContext(roomID:)` as the eligibility and runtime input. Pass its `ForwardMenuContext` to `MessageMenuRules.items(..., forward:)`, the `MessageOverlayRequest`, and `MessageMenuRules.isEnabled(..., forward:)` for the overlay and VoiceOver. Forward is between pin/unpin and edit. Nil means this chat has no picker route. A context whose `canOpenPicker` is false keeps the offered item disabled while the runtime is unavailable or a picker transition is pending. The title points to the existing exported forward key and the current glyph is the Kit arrow. The `perform` forward case is the compile-time seam for the Opus action.
2. When the cover closes, rederive `MessageMenuRules.forwardEventID(for:)`. Bind the action to `model.prepareForward(roomID:eventID:stillCurrent:)`. The supplied closure should be false once the picker or source chat has been replaced, dismissed or switched accounts. Cancel the preparation task on dismissal. The returned `RoomForwarding.preview` is the exact projection that will send, with `kind`, `body`, optional filename and supported formatting. Use only the display fields in the view. The raw JSON contains encrypted media descriptors or protected provenance and is for the send path.
3. Load `targets()` once for each picker presentation and refresh on joined-room or permission changes. `targets(matching:)` applies local search over both visible title and Matrix display name. It returns ordered `id`, `name`, `avatarURL`, `isEncrypted` and an optional refusal. A disabled encrypted-attachment target remains in the list. The SDK data layer repeats scope, membership, send power, tombstone and encryption checks on selection. A company message can go to a room of that company or to the owner's assistant. Directory state must resolve for ordinary targets. Company-guarded files are refused even if only the original revision carried that marker. Client-side assistant invocation for a desktop-local agent is still a desktop path. Phone emits the event and cloud assistants can consume it.
4. Call `send(to:)` once for a confirmed selection. Success is `.sent(eventID:)` for a raw send or `.queuedAttachment` for the native media path. If the preview changed during the picker, `.sourceChanged` requires a new preview and decision. `.deliveryUnconfirmed` means inspect the destination or existing failed echo before trying again. The native raw-send API assigns its own transaction ID, so the picker coalesces repeat taps after success and blocks repeats after an ambiguous write. The attachment adapter removes source thumbnails before the encrypted re-upload.

### Link previews

Create `model.openRoomLinkPreviews(roomID:)` once for the displayed chat and current Matrix session. For a row whose `item.linkPreviewURL` is available, call `card(for:)` from the row's visibility task, keyed by room, session, event ID and URL. A nil result is the plain link. When SwiftUI reuses the bubble, discard a result from an earlier key. Call `close()` when the chat or session changes. Plain room cards go above `DeliveryLine` in the flat or grouped row. Tap the original URL through the existing `LinkPolicy` route. Open Graph titles and descriptions are plain display text and the optional image is bounded Matrix thumbnail data.

### Room mentions

Superseded by Decision 7 below. Include the room option only when `store.offersRoomMention` is true. The room pick calls `await store.pickRoomMention()`, which rechecks power, refuses a pick from an old draft or generation, and inserts `@channel `. The attached store owns the initial power read and cached `m.room.power_levels` subscription (company channels with platform authority only), and cancels on room exit or session renewal. People picks keep the existing APIs. Read `item.hasRoomMention` for intentional incoming rendering. Attachment-caption and edit UIs keep their existing mention behavior.

### Upgrades and earlier history

Read `session.roomUpgradeContinuity(roomID:)` on open and again after a room-list or room-info update. A nil successor means no banner. `.join(roomID:)` and `.open(roomID:)` are explicit actions. `.waitingForState` is a joined replacement whose create state has yet to arrive. `.unavailable` preserves the active transcript and has no navigation action. On tap, call `followRoomUpgrade(roomID:replacementID:)`. Open only a matching `.open(roomID:)` result and only while the original view and Matrix session are current. Use the existing room access routes, including directory authorization in Team Space. If sync has not published the just-joined room yet, re-read on the next publication. An invalid backlink after joining leaves the old transcript in place. No automatic leave of either room. Link `earlierRoomID` back to the authorized old transcript through the same existing navigation, even when the main roster hides that row.

## SDK test failure on the first locked run (`7bb256b`)

`testPinnedSDKQueuesTextAndUsesCurrentRoomMentionPower` saw 1 of 4 sends (`Ordinary text`) at its 6 s deadline. The test took 46.7 s, and the simpler forward test took 26 s on the same loopback fixture. The likeliest cause is Matrix requests running close to the fixture's 3 s client timeout on the loaded USB build volume. The run kept no Rust trace, so this is inferred from the timings and the parked-queue pattern. A send-queue request that times out is a recoverable error. The SDK then disables that room's queue and parks the rest of it until something re-enables it. In production that happens on the next send, "Thử lại", foreground or network regain (`SessionLifecycle.wakeSendQueues`, `SDKTimelineSource.enableSendQueue`). The test never re-enabled the queue, so the next three sends could not go out however long it waited. The mention content is built before any SDK call, and the power-read assertions passed. That rules out a mention bug.

Fix: the test subscribes to `Client.subscribeToSendQueueStatus`, records every room error, and re-enables the room's queue after each one, as production does. The failure message now includes those errors. The fixture request timeout is 10 s instead of 3 s, and the wait is 30 s. The wait is longer because each parked send needs a fresh request. The longer wait alone would not have fixed this run.

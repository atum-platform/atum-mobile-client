# Phone chat parity ML1 · Threads and shared pins

S4 and S5 engine work on mobile base `f9231683f80bc378b79299a43ea14af713be548b`. The phone engine reuses the Team Space thread store and Matrix thread operations. The Opus UI pass adds the group thread entry, pushed thread and list screens, root summaries, the details preview, the pin menu actions and the shared pinned list. The S4 engine follow-up adds group main-transcript projection and per-root summaries. Status: partly built, with live interop and device acceptance pending. ML6 starts after the assembled ML1 outcome merges.

## Native inventory and desktop contract

- The mobile roster uses direct classification plus joined and invited member count in `ios/App/LiveRosterRows.swift`. `LiveAppModel.conversationInfo` applies existing app-bot and assistant recognition, including the two-member limit from `MobileRosterPolicy.swift`. The scope in `RoomThreadsReads.swift` combines those facts with cached create state and the company directory. It admits ordinary human groups, including an invited assistant, and gives people DMs pins only. A typed room, Notes, private Chief of Staff, a legacy moved app-bot room, or an assistant or app DM does not acquire these actions.
- Team Space already used `Room.threadListService`, `Room.timelineWithConfiguration`, the existing `LiveConversationStore`, and private `Room.sendSingleReceipt`. The engine continues to use them. The native list provides item changes and paging through `subscribeToItemsUpdates` and `paginate`. The focused timeline owns `m.thread` sends and private threaded reads. The existing Atum follow account-data operation remains portable with desktop. MSC4306 server push subscriptions have a separate explicit entry point.
- The selected [Swift producer](https://github.com/atum-platform/atum-matrix-rust-components-swift/blob/66c18d378d44d9ad61946f08b926514cccb14fb5/Sources/MatrixRustSDK/matrix_sdk_ffi.swift) remains `26.10.15-atum.2`. Its Rust base implements [pin and unpin](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk/src/room/mod.rs#L4739) by reading current synced pin IDs and sending new `m.room.pinned_events` state. Phone uses those methods, `Room.getPowerLevels`, `Room.stateEvents`, `Room.subscribeToRoomInfoUpdates`, and `.pinnedEvents` focus. It bounds writes to 100 unique, valid event IDs, like desktop.
- The applicable desktop contract is [PR #156](https://github.com/atum-platform/atum-desktop/pull/156) at `56d4483ce2173faae5a2e9393cc0843b5e2e8fca`, specifically [room scope](https://github.com/atum-platform/atum-desktop/blob/56d4483ce2173faae5a2e9393cc0843b5e2e8fca/apps/desktop/src/matrix/thread-room.ts), [thread sends and reads](https://github.com/atum-platform/atum-desktop/blob/56d4483ce2173faae5a2e9393cc0843b5e2e8fca/apps/desktop/src/matrix/threads.ts), and [shared pin writes](https://github.com/atum-platform/atum-desktop/blob/56d4483ce2173faae5a2e9393cc0843b5e2e8fca/apps/desktop/src/matrix/pinned-events.ts). The other inspected desktop heads are #154 `49e7b533` (filters), #155 `c2099ee6` (push rules), #157 `ada85be8` (rich events), and #158 `3eca77b1` (search). They do not add a second thread, pin or follow wire format.

## Opus integration contract

1. Use `LiveAppModel.sharedChatActions(roomID:)` from the current live room. The new thread entry applies to `.peopleGroup`. Keep current Team Space entry points for `.teamSpace`. Pass the room gate into `MessageMenuRules.items(for:in:threads:)`, then use `threadRootID(for:)` for the action. An existing thread reply cannot become a nested root. Close/reset the pushed screen and cancel its reads on account/session replacement, room exit, or loss of group eligibility.
2. Retain one `openGroupThreadList(roomID:)` instance for an open room. Read `roots()` for root/count/latest message summaries, listen to `updates()`, and use `canPaginate` and `paginate()` to load more. `threads()` adds the existing follow and bounded homeserver notification projection for recent/all lists. That projection can lack unread highlights if the notification endpoint is unavailable or the event predates its bounded history. Refresh it after follow or mark-read. A load error is distinct from a successful empty list.
3. `openGroupThread(roomID:rootID:draft:focusEventID:)` validates the root in that room and returns an attached `LiveConversationStore`. Keep the usual store composer, attachments and mentions; close the store on dismissal. `readGroupThread` marks a confirmed reply read from the list with a private thread receipt. Use `setGroupThreadFollow` for Atum follow, whose desktop key is `io.atum.thread_attention.v1`. `setGroupThreadSubscription` performs explicit MSC4306 server subscription operations when supported. The latter is independent of follow and of the room notification mode.
4. The group main transcript shows roots, top-level messages, and historical `io.atum.result` assistant answers. Ordinary thread replies appear in the native focused timeline. The transcript's existing `ChatThreadSummaries.threads[rootID]` contract now includes roots known by the main SDK timeline even before the thread list loads them. The details preview and All threads continue to read the paged list. Summary alignment and navigation use the existing presentation.
5. For eligible chats, retain `openRoomPins(roomID:)` and subscribe to `updates()`. Re-read `snapshot()` on the initial view, sync, and after each local mutation. It returns ordered IDs, write power, and a pending-write indicator. `entries(for:)` uses native pinned-events focus, preserves state order, omits known redactions, and represents unavailable events without content. Replace stale entries after a newer snapshot. Read-only list access survives demotion. Use `MessageMenuRules.pinEventID(for:in:canChange:)` for a settled event and call `setPinned(_:eventID:)` with the desired state.
6. Disable conflicting edits while `awaitingSync` is true and refresh after the SDK publishes the next pin state. A second local write in the same room while a request is active or awaiting state sync returns `.awaitingSync`. `.forbidden` covers demotion, including an authoritative stale-write rejection. `.invalidTarget`, `.invalidState`, `.limit`, `.unavailable` and `.failed` give the presentation recoverable error categories. An already-satisfied valid intent succeeds without a write. The UI should never replace the displayed pin list optimistically with a stale copy.

Two clients can start with the same pin state and write simultaneously. Matrix has no compare-and-swap for this state event, so one update can be lost. The homeserver's resolved state observed through sync is authoritative. The local guard covers overlapping and acknowledged phone writes, and each new intent starts from SDK state. This uses the existing room and state event without lock services or private wire fields.

## S4 transcript follow-up

- The pinned FFI's `TimelineFocus.live(hideThreadedEvents:)` hides all threaded events. `TimelineFilter` accepts event kinds and types and has no content predicate for `io.atum.result`. The main timeline therefore keeps the native live focus with hiding disabled. `ItemMapper` carries the SDK's `threadRoot` and identifies a result object on the original event, including when the latest edit omits it. `TimelineProjector` filters standard replies after applying SDK diffs. `TimelineBuffer` keeps those replies at their SDK indices and excludes them from main append and jump-pill accounting. [Pinned Swift bindings](https://github.com/atum-platform/atum-matrix-rust-components-swift/blob/66c18d378d44d9ad61946f08b926514cccb14fb5/Sources/MatrixRustSDK/matrix_sdk_ffi.swift#L46589)
- The room gate is shared with group thread actions. Only an eligible group main store enables the projection. People DMs, assistant and app DMs, Notes, Team Space, and focused group threads continue to project their existing events. Group main reads send a scoped `main` receipt on a visible top-level event and preserve the share-activity preference. A focused thread still sends a private receipt for the thread root's scope. [SDK receipt routing](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk-ui/src/timeline/controller/mod.rs#L177)
- The mapper reads `MsgLikeContent.threadSummary` for settled message roots. A positive count stands on its own while the latest embedded event is pending. Once available, the SDK supplies the latest reply ID, time and sender profile. `GroupRoomLive` feeds these roots into the existing capsule dictionary and keeps list entries as fallback when the timeline supplies no aggregate. `RoomThreadList` reads public and private receipts from the SDK's local store. The latest reply's own sender or a receipt targeting it clears unread. A newer unthreaded legacy receipt can also cover it, using the receipt timestamp to approximate event ordering when the IDs differ. Missing latest details or a receipt lookup failure falls back to the loaded list's unread state when available. The transcript refreshes receipt state on root and list updates and on the existing return-from-thread refresh. [Pinned thread aggregate and local receipt APIs](https://github.com/atum-platform/atum-matrix-rust-components-swift/blob/66c18d378d44d9ad61946f08b926514cccb14fb5/Sources/MatrixRustSDK/matrix_sdk_ffi.swift#L18896)

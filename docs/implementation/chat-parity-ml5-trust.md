**Atum MAS configuration.** Repository snapshot `fd831c390ad868688157e2af3999f6b126f0d89f` selects Synapse v1.161.0 and MAS 1.24.0, with delegated auth enabled. That Synapse handler permits a first `POST /keys/device_signing/upload` without UIA for an authenticated MAS session per MSC3967. A different established identity requires `m.oauth` or the legacy cross-signing reset stage, unless a separate approval already made the master key replaceable. MAS approval is for replacement. Neither such approval nor a reset is part of phone-first setup. This is repository and upstream source evidence. [Atum configuration](https://github.com/atum-platform/atum-platform/blob/fd831c390ad868688157e2af3999f6b126f0d89f/deploy/chat/compose.yaml#L42) · [Delegation](https://github.com/atum-platform/atum-platform/blob/fd831c390ad868688157e2af3999f6b126f0d89f/deploy/chat/prepare.py#L112) · [Synapse v1.161.0 handler](https://github.com/element-hq/synapse/blob/v1.161.0/synapse/rest/client/keys.py#L516)

**Custody limit.** Builder auto-signing is safe when the SDK sees an already established identity in its key query. Synapse v1.161.0 checks for first setup before separate awaited key writes. The check and writes do not share a conditional transaction, so a concurrent first upload or a currently approved replacement window can invalidate a client-side absence check. Backup creation has the same gap. The backup endpoint serializes version creation, and each create establishes a new active version. The pinned SDK sends a bare create after the existence GET. Two devices can both see absence and the second create can supersede the first backup. The native fixture stages that interleaving. The same limitation applies to the existing-identity recovery setup if two already trusted devices race it. A same-store client rebind would add another ownership transition but would still have these server mutation gaps. [Signing handler writes](https://github.com/element-hq/synapse/blob/v1.161.0/synapse/handlers/e2e_keys.py#L1049) · [Signing store transaction](https://github.com/element-hq/synapse/blob/v1.161.0/synapse/storage/databases/main/end_to_end_keys.py#L1838) · [Backup version creation](https://github.com/element-hq/synapse/blob/v1.161.0/synapse/handlers/e2e_room_keys.py#L334)

**Minimal proposal.** Keep signing and backup auto-initialization off in the shared phone builder. For an explicit, custody-preserving setup, extend the platform contract with atomic create-if-absent semantics for first signing and for initial recovery writes, including the active backup and default secret-storage key. Reuse the SDK's existing key generation and signing. A small future FFI addition should invoke that bootstrap on the live client, surface a typed conflict, challenge or transport failure, and confirm the server accepted this identity before backup setup. If the server returns an existing identity, offer verification or restore. Bring the generated recovery key back through the existing generation-scoped device-only Keychain and save receipt. The pin, runtime and shared builder need no edit for this evidence checkpoint.

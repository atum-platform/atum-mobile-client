Status at 27 November 2026. Partly built. S7 and S9 have nonvisual engines. S8 has existing-identity recovery setup and restore. Fresh phone-first cross-signing, presentation and release interop are open.

## Native inventory and preservation boundaries

The phone base is `f9231683f80bc378b79299a43ea14af713be548b`. The SDK project and package pin remains [26.10.15-atum.2](https://github.com/atum-platform/atum-matrix-rust-components-swift/tree/66c18d378d44d9ad61946f08b926514cccb14fb5). [Generated FFI](https://github.com/atum-platform/atum-matrix-rust-components-swift/blob/66c18d378d44d9ad61946f08b926514cccb14fb5/Sources/MatrixRustSDK/matrix_sdk_ffi.swift#L5449)

- **S7.** The pin supplies request, acknowledge, accept, start, approve, decline and cancel. Incoming verification uses the SDK's request and SAS streams. The phone limits this UI contract to the signed-in account's other devices. The pinned Ready callback occurs in both directions, so the requester starts SAS and the responder waits for peer Start. An independent transition by both clients can surface as unavailable with this pin. The native controller retains cancel metadata across flows. The app uses closed reason codes and ignores stale presentation actions by attempt ID. [Selected Rust verification controller](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/bindings/matrix-sdk-ffi/src/session_verification.rs#L113)
- **S8.** In the producer source, `reset_identity` disables and deletes active backup and clears the default secret-storage event **before** requesting interactive authentication. A preflight lookup cannot make that operation safe against concurrent setup from a second device. The lane uses `enableRecovery` after explicit setup on an SDK-verified device and blocks if native recovery already exists or the server reports an active backup. Only Matrix Rust generates or validates the key. `recover` restores without rotation or backup repair. The explicit setup operation serializes with restore and key-save confirmation. The newly minted key is retained in the main app's device-only Keychain until successful confirmation. If the process dies before Rust returns the key or Keychain persistence fails, availability is partial and the engine does not automatically rotate the key or replace the backup. The stock restore flow still imports a user-supplied key without exporting it locally. [Selected Rust identity reset](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk/src/encryption/recovery/mod.rs#L438) · [Selected recovery enable future](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk/src/encryption/recovery/futures.rs#L92)

An explicit private call requires current SDK device verification, enabled recovery, an enabled backup, a device-only confirmation for the synced default storage key, complete session sync and positive human classification from a platform alias lookup. Ongoing recovery and stale session actions fail closed. Rust translates `isEncrypted` into an initial `m.room.encryption` state event carrying `m.megolm.v1.aes-sha2`. Private history begins at join. Private DMs reuse eligible existing encrypted DMs and keep a separate create attempt from the plain path. Private groups take a stable request UUID for single dispatch and require the same name and participants when retried. Ambiguous SDK results are retained for the live session. Old rooms are not converted. [Selected Rust room parameters](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/bindings/matrix-sdk-ffi/src/client.rs#L3152)

## Opus and coordinator integration

- Bind to the current runtime's `deviceVerification`. Observe `state` and retain its UUID with the presented action. Attach `listen()` after initial sync if the surface will receive invitations. Use `request()` for phone-first request, `accept(id)` for an incoming invitation, `compare(id, matches:)` only from the matching comparison, and `cancel(id)` for explicit cancellation before confirming. A match action commits local approval to the SDK. Native `.finished(.matched)` is the only SAS success. Once a user has explicitly approved, a peer completing the transaction concurrently with cancellation may already have committed it. Render long-lived trust from `securitySnapshot().sessionVerified`, independently of the recovery result and local device ID. Recreate observation when the live runtime changes. Ensure sign-out or teardown dismisses sensitive views.
- Connect an explicit Security action to `setupRecovery()`. A pending save ID is resumable while the Keychain binding matches. `.verificationRequired` means an existing identity must verify or restore. `.crossSigningBootstrapUnavailable` means no identity was found and the live client pin cannot bootstrap it safely. Recovery-state `.unknown` needs initialization or sync. `.existingRecovery` routes to restore and preserves existing data. Keep raw SDK error details out of view and diagnostics. The coordinator owns builder integration. The SDK's no-UIA builder facility is a discovery, and an explicit rebind needs a proved custody-preserving transition before enabling it in the product. The pinned FFI cannot present a UIA challenge for this safe route.
- Use `withRecoveryKey(id, use:)` only on the explicit key reveal/copy surface. Treat the key and its rendered content as sensitive, including app-switcher previews, state restoration, screenshots in tests and analytics. Clear transient view state on dismissal, backgrounding or account change. An explicit Copy action uses a local-only, expiring pasteboard item. `confirmRecoveryKeySaved(id)` is the manual fallback after the person has stored the key outside the app. A copy tap does not confirm.
- Add the generation-scoped recovery save record to the existing local sign-out and erasure custody journal at integration. Include `pendingSaveID` in the preexisting unsaved recovery warning before a sign-out can strand the generated key, and delete the record on explicit account erasure. Token refresh should retain the record for the same Matrix device and generation.
- **Save to Passwords** goes first when available. Call `saveRecoveryKey(id, using:)` with a main-actor closure that invokes `ASCredentialDataManager().save(password:for:title:anchor:)` from the presenting window. The installed Xcode interface marks the method available starting in iOS 26.2. Keep manual Copy and confirmation on 26.0 and 26.1. Use a dedicated recovery-only HTTPS credential scope and a distinct account-scoped synthetic username. The scope must be covered by the signed app's `webcredentials` entitlement and a verified associated-domain declaration. The current entitlement lists the API origin, and it does not establish a dedicated recovery origin. Confirm the actual scope and absence of login AutoFill interference with the coordinator before assuming the platform save is available. Pass the key only as the system credential's password, never in a URL, action identifier or title. Complete the closure successfully only on system success. A cancelled/unavailable save keeps the pending record and the manual fallback. The runtime rechecks current custody and the storage key after the system prompt; app-side confirmation never migrates across accounts. The system may use the user's preferred password manager. [Apple credential save API](https://developer.apple.com/documentation/authenticationservices/ascredentialdatamanager/save%28password%3Afor%3Atitle%3Aanchor%3A%29) · [Apple AutoFill scope](https://developer.apple.com/documentation/authenticationservices/asautofillurlscope)
- Hide Private until `securitySnapshot().canCreatePrivateChat` and the coordinator's real-device release proof. Refresh after sync, setup, restore, SAS, a return to foreground and account replacement. Keep the default off. Positive human lookup evidence must match the selected MXID at dispatch, including a roster selection originally inferred from room membership. Use `createPrivateDirectRoom(inviting:)` or `createPrivateGroup(name:inviting:requestID:)`. Keep the UUID across retry for the exact group creation intent. Route to the returned exact room ID after sync. Keep a pending/ambiguous result associated with that intent. Reusing an existing plain room by target or matching a group by name would bypass the Private selection. The current phone has no ordinary post-creation member-invite dispatch path. If one lands with this feature, pass private invite candidates through the same positive-human evidence gate and block unknown encryption state at dispatch.
- SAS, recovery and private room integration intentionally stay in app/runtime source. Regenerate the Xcode project once at assembly to register the new `App/Security` and `AppTests` files.

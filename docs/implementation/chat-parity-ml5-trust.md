**Custody limit.** Builder auto-signing is safe when the SDK sees an already established identity in its key query. Synapse v1.161.0 checks for first setup before separate awaited key writes. The check and writes do not share a conditional transaction, so a concurrent first upload or a currently approved replacement window can invalidate a client-side absence check. Backup creation has the same gap. The backup endpoint serializes version creation, and each create establishes a new active version. The pinned SDK sends a bare create after the existence GET. Two devices can both see absence and the second create can supersede the first backup. The native fixture stages that interleaving. The same limitation applies to the existing-identity recovery setup if two already trusted devices race it. A same-store client rebind would add another ownership transition but would still have these server mutation gaps. ## S8 auto-initialization follow-up

The 28 November owner decision applies to a phone-first account with no server identity. Trust setup runs out of band, presents no interactive authentication, and must preserve active identities and backups. The shared phone builder retains its current flags because the selected binary cannot implement those conditions together.

- `autoEnableCrossSigning(true)` can publish the first identity in the background. On a 401, the SDK caches its generated identity before the request fails. That cache entry suppresses the upload on the next builder initialization. The loopback fixture lifts the rejection before reopening the same encrypted store and checks for a new upload. Retrying publication of the same keys needs a native API beyond the pinned Swift interface. The exposed `resetIdentity()` deletes recovery before authentication. [Selected Rust bootstrap and initialization](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk/src/encryption/mod.rs#L1566)
- `autoEnableBackups(true)` runs separately after signing, even when signing fails or the account already has an identity. It creates an active backup and stores its encryption key in the SDK store, leaving secret storage disabled and the user without a recovery key. A separate `enableRecovery()` call generates the user key. Two clients can race its backup create and default secret-storage write because each uses an unconditional server mutation. [Selected Rust recovery setup](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk/src/encryption/recovery/mod.rs#L602) · [Selected recovery enable future](https://github.com/matrix-org/matrix-rust-sdk/blob/97a1589b70bd122c1d66e0d68ea008d8554076a5/crates/matrix-sdk/src/encryption/recovery/futures.rs#L75)
- A viable implementation needs a non-interactive SDK entry point that retries the pending identity on the same live device and reports an accepted or conflicting server identity. The platform needs atomic first-create conditions for signing, backup and the default secret-storage key. The app can then run the native operation independently of sync, retain the key in the existing generation receipt and record closed diagnostics for retryable outcomes.

### Recovery receipt contract

- `securitySnapshot().pendingSaveID` is the UUID of the pending generation-scoped receipt, even when reading the default key fails. `recoveryKeyConfirmed` requires a matching synced default storage key ID and a confirmed receipt with no pending secret. `sessionVerified`, `backupEnabled` and `recoveryEnabled` remain independent native SDK facts. Private requires all four confirmed facts.
- `setupRecovery()` returns an already-pending UUID before checking native verification or provisioning anything else. Calling `withRecoveryKey(id, use:)` and `saveRecoveryKey(id, using:)` uses that UUID on the current runtime. Refresh the snapshot after a successful save.
- `pendingRecoverySaveID()` is a synchronous, local-only lookup for the sign-out warning. It checks live session custody, returns `nil` for a missing or confirmed receipt, and throws when custody or Keychain state is unavailable. Account UI and sign-out transaction wiring remain integration work. Keep the existing legacy recovery-save path alongside this check. Read again at the destructive boundary, and stage generation-scoped receipt deletion with the other local records.
